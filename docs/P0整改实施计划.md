# P0 整改实施计划

## 背景

本计划覆盖整改任务管理中 P0-01 至 P0-06：安全控制 onboarding 调试绕过、处理未实现日历同步、统一 CI Flutter SDK、禁止 iOS 构建静默失败、建立受控初始化恢复流程，以及删除签名脚本默认口令。

## 约束

- Flutter 版本固定为 3.44.1。
- 工作区已有用户未提交改动，不回滚或覆盖无关文件。
- 不新增未经验证的日历插件；未实现能力先从用户入口移除。
- 不打印、索取或写入真实密钥。
- 本地数据重置是潜在破坏性操作，只实现需要用户明确确认的 UI，不在实现或验证期间执行。

## 方案 A：最小可发布整改

### 思路

采用受控隐藏、构建期开关和启动重试，优先消除 P0 风险而不引入新的平台依赖或大型架构重写。

### 改动文件

- lib/main.dart
- lib/pages/settings/settings_page.dart
- lib/common/services/calendar_sync_service.dart
- .github/workflows/release.yml
- scripts/setup_github_secrets.sh
- docs/整改任务管理.md

### 优点

- 改动范围可控，能在今天完成。
- 直接消除错误 onboarding、空壳日历入口、CI SDK 漂移、iOS 静默失败和默认口令风险。
- 启动失败可安全重试，且不会在测试中执行数据删除。

### 缺点

- 不提供真实系统日历同步；该能力会暂时下线。
- 不会一次性完成 DatabaseService 架构拆分或 Hive 自动修复。

### 风险

- 现有已打开的日历同步设置需要在启动时被安全关闭。
- CI 改动只能通过 YAML 静态校验和本地 Flutter 验证，无法在本地完整模拟 GitHub 签名环境。

### 验证

- Flutter format。
- Flutter analyze。
- Flutter test。
- Flutter build web。
- grep 确认 release workflow 不含 3.24.0 和 continue-on-error。
- shell 语法检查签名脚本。

## 方案 B：完整原生日历与数据恢复工程

### 思路

引入原生日历插件、事件 ID 映射、Android/iOS 权限、数据重置和导出诊断服务，以及针对损坏 Hive Box 的自动恢复策略。

### 改动文件

除方案 A 文件外，还需修改 pubspec、Android/iOS 配置、数据库模型、服务测试与平台说明。

### 优点

- 日历同步能力可真正交付。
- 启动失败可提供更完整的数据诊断和恢复。

### 缺点

- 涉及平台权限、插件选择和数据删除语义，无法在当前时间范围可靠验证。
- 风险和回归面显著更大。

### 风险

- 新插件在 Web、iOS、Android 的行为不一致。
- 错误的数据恢复实现可能造成用户本地数据丢失。

### 验证

除方案 A 外，需要真机或模拟器验证系统日历写入、更新、删除、拒绝权限、离线和已有用户数据迁移。

## 推荐

推荐方案 A。

1. 它把目前的虚假或不安全行为改为真实、可验证的行为。
2. 它避免在没有明确平台验收的情况下承诺日历同步。
3. 它先为后续 P1 数据架构与平台能力建设保留清晰边界。

## 落地步骤

1. 将 onboarding 绕过改为仅由 dart-define 在 debug 模式启用。
2. 把初始化抽取为可重试 bootstrap，ErrorApp 使用状态管理的受控重试，提供确认式数据重置入口。
3. 移除设置页日历同步开关，并把 CalendarSyncService 标记为不可用且安全关闭遗留设置。
4. 将 Android、iOS CI Flutter 版本更新至 3.44.1，移除 iOS 构建的 continue-on-error，并让 IPA 上传只在成功时执行。
5. 让签名辅助脚本校验环境变量、拒绝空值，不再输出默认口令。
6. 格式化、分析、测试、Web 构建，更新 P0 任务状态和验证记录。
